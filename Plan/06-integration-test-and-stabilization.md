# 06. 통합 테스트 및 안정화 설계

> 레거시 RPS 통합 설계 (2026-07-24): 기존 테스트 매트릭스는 v1 회귀 참고용으로 보존한다. Triage Trace 통합 기준은 Pose tracking·pointer 안전 비활성화·비의료 고지를 포함해 후속 활성 Task에서 확정한다.

## 목적

웹캠 입력부터 Unity UI 표시까지 전체 경로가 기능·성능·복구 요구사항을 만족하는지 검증하고, 실제 환경에서 발생하는 판정 흔들림, 통신 지연, 연결 끊김 및 자원 누수를 조정한다. 검증 결과를 재현 가능한 기록으로 남겨 초기 버전의 완료 여부를 판단한다.

## 구현 범위

- Python 모듈 단위 테스트 전체 실행
- Unity EditMode 및 PlayMode 테스트 전체 실행
- Python–Unity WebSocket 계약 테스트
- 실제 웹캠 기반 끝단 기능 테스트
- 좌우 손, 손 방향, 거리, 조명, 배경 조건 테스트
- 연결 순서, 서버 종료, 재시작 및 자동 재연결 테스트
- 지연 시간, 처리 FPS, 송신 빈도, 메모리 안정성 측정
- 임계값과 안정화 창 조정
- 실행 방법, 문제 해결, 알려진 제약 문서화
- 완료 기준 판정과 후속 작업 등록

새로운 기능과 초기 범위 밖의 확장은 이 단계에서 추가하지 않는다. 발견된 기능 요구는 별도 후속 작업으로 기록한다.

## 설계 내용

### 테스트 계층

```text
1. Python unit tests
   - model / classifier / stabilizer / serializer
2. Python component tests
   - tracker adapter / publisher
3. Unity EditMode tests
   - JSON parser / validation / presentation mapping
4. Unity PlayMode tests
   - main-thread queue / UI / lifecycle
5. Contract tests
   - Python JSON -> Unity parser
6. End-to-end manual tests
   - Webcam -> Python -> WebSocket -> Unity UI
7. Soak and recovery tests
```

하위 계층 실패를 해결한 뒤 상위 통합 테스트를 진행한다. 카메라가 필요 없는 테스트는 자동화해 반복 실행 비용을 낮춘다.

### 테스트 환경 기록

결과에는 최소 다음 환경을 기록한다.

- 운영체제
- Python 버전과 의존성 버전
- MediaPipe API 및 모델 정보
- Unity 에디터 버전과 WebSocket 패키지 버전
- 카메라 장치와 요청/실제 해상도
- 서버 URI
- 제스처 임계값, 안정화 창, 송신 빈도

환경 정보가 없는 정확도 수치는 재현하기 어려우므로 완료 근거로 사용하지 않는다.

### 기능 테스트 매트릭스

| ID | 조건 | 기대 결과 |
|---|---|---|
| F-01 | 오른손 주먹 | Unity에 `주먹` |
| F-02 | 오른손 가위 | Unity에 `가위` |
| F-03 | 오른손 보 | Unity에 `보` |
| F-04 | 왼손 각 제스처 | 오른손과 동일한 의미로 표시 |
| F-05 | 규칙 밖의 자세 | `손 모양을 확인해 주세요` |
| F-06 | 손이 없음 | `손을 카메라에 보여 주세요` |
| F-07 | 손이 사라졌다 다시 등장 | `NO_HAND` 후 새 제스처 복구 |
| F-08 | 빠르게 제스처 변경 | 안정화 지연 내 최신 확정 결과 표시 |
| F-09 | 잘못된 JSON 주입 | Unity가 종료되지 않고 메시지 무시 |
| F-10 | 지원하지 않는 버전 | Unity가 적용하지 않고 경고 |

각 제스처는 한 번의 성공으로 끝내지 않고 여러 번 반복해 성공/오분류 횟수를 기록한다.

### 환경 조건 매트릭스

- 밝은 실내 / 낮은 조도
- 단색 배경 / 복잡한 배경
- 카메라 가까이 / 권장 거리 / 멀리
- 손바닥 / 손등
- 손의 좌우 기울임과 제한된 회전
- 화면 중앙 / 가장자리
- 좌손 / 우손

초기 범위에서 지원하기 어려운 극단 조건은 실패를 숨기지 않고 알려진 제약과 권장 사용 조건으로 문서화한다.

### WebSocket 계약 테스트

Python 메시지 빌더가 생성한 실제 JSON fixture를 Unity 파서 테스트 입력으로 공유한다.

검증 항목:

- 모든 필수 필드와 정확한 대소문자
- `type`과 `version`
- 모든 gesture 및 handedness enum
- `NO_HAND` 불변 조건
- confidence 경계값 `0.0`, `1.0`
- 큰 timestamp 및 sequence의 C# 정수 범위
- 추가 필드가 있는 메시지
- 누락, 잘못된 형식, 잘못된 enum 메시지

계약 fixture 변경은 양쪽 테스트 리뷰 없이 단독으로 수행하지 않는다.

### 연결 및 복구 테스트

| 시나리오 | 기대 결과 |
|---|---|
| Python 실행 후 Unity 실행 | 즉시 연결 및 결과 표시 |
| Unity 실행 후 Python 실행 | 재연결을 거쳐 자동 연결 |
| 연결 중 Python 정상 종료 | Unity가 끊김 상태와 재연결을 표시 |
| Python 재시작 | Unity가 Scene 재시작 없이 복구 |
| Unity Play Mode 종료 | Python 연결이 정리되고 Unity 작업이 남지 않음 |
| 포트 점유 | Python이 명확한 오류를 내고 비정상 루프에 빠지지 않음 |
| 카메라 점유/부재 | Python이 원인을 표시하고 자원을 정리 |
| 일정 시간 메시지 중단 | Unity가 데이터 만료 상태 표시 |

### 성능 지표

측정 대상:

- 카메라 캡처 및 MediaPipe 처리 FPS
- 원시 판정에서 안정화 확정까지 걸린 프레임 수와 시간
- 초당 WebSocket 메시지 수
- 메시지 `timestamp`부터 Unity 적용까지 끝단 지연
- CPU 및 메모리 사용 추이
- 장시간 실행 중 연결 수와 작업 수

초기 목표는 사용자에게 자연스러운 실시간 반응과 10~20Hz 이하의 전송이다. 정확한 허용 지연과 최소 FPS는 기준 개발 PC에서 측정한 후 문서에 수치로 확정한다.

### 안정화 조정 순서

1. 손 추적 품질과 handedness 정책을 먼저 확인한다.
2. 단일 프레임 분류 fixture를 기준으로 각도와 거리 임계값을 조정한다.
3. `UNKNOWN` 오탐과 잘못된 세 제스처 확정 사이의 균형을 확인한다.
4. 안정화 창 크기, 최소 표, `NO_HAND` 연속 프레임 수를 조정한다.
5. 송신 빈도와 Unity 데이터 만료 시간을 조정한다.
6. 끝단 지연을 재측정한다.

네트워크나 안정화 설정으로 지속적인 잘못된 단일 프레임 분류를 감추지 않는다.

### 장시간 테스트

최소 장시간 시나리오를 정의해 다음을 관찰한다.

- Python과 Unity 메모리의 지속 증가 여부
- 카메라 프레임 처리 중단
- WebSocket 재연결 작업의 중복
- 로그 파일 또는 콘솔 출력 폭주
- sequence 진행과 최신 메시지 유지
- 종료 시 프로세스와 포트 정상 해제

문제가 발생하면 발생 시각, 직전 연결/제스처 이벤트, 재현 절차를 기록한다.

### 결함 분류

| 증상 | 우선 확인 위치 |
|---|---|
| 랜드마크가 없음 | 카메라, MediaPipe 설정, 조명 |
| 손가락 상태가 틀림 | 특징 계산, 좌표/handedness 정책 |
| 원시 결과는 맞고 확정이 느림 | 안정화 창과 최소 표 |
| Python JSON은 맞고 Unity 표시가 틀림 | C# 파서, enum 매핑, 메인 스레드 큐 |
| 연결이 반복됨 | URI, 포트, 수명 주기, 재연결 상태 기계 |
| 화면 결과가 오래됨 | 송신 큐, timestamp, Unity 데이터 만료 |

### 완료 산출물

- 자동 테스트 결과
- 수동 테스트 체크리스트와 결과
- 환경 및 성능 측정표
- 확정 설정값
- 실행 순서와 종료 방법
- 자주 발생하는 오류와 해결 방법
- 알려진 제약
- 미해결 결함과 후속 `Tasks/` 항목

## 입출력

### 입력

- 01~05 단계의 구현 결과
- Python 단위·통합 테스트
- Unity EditMode·PlayMode 테스트
- 실제 웹캠과 테스트 환경
- 버전 1 JSON 계약 fixture
- 프로젝트 완료 기준

### 출력

- 전체 테스트 결과와 재현 환경
- 조정된 분류 및 안정화 설정
- 검증된 WebSocket·Unity 동작
- 실행 및 문제 해결 문서
- 완료 여부와 남은 위험 요소
- 후속 작업 목록

## 주의사항

- 테스트 결과 없이 임계값을 감으로 확정하지 않는다.
- 정확도와 지연 시간을 함께 본다. 안정화 창을 크게 하면 흔들림은 줄지만 반응이 느려진다.
- 수동 테스트의 성공 사례만 기록하지 말고 반복 횟수와 실패 조건을 함께 남긴다.
- WebSocket 연결 성공만으로 끝단 성공으로 판단하지 않는다. Unity UI 반영까지 확인한다.
- 카메라 영상 저장이 필요해지면 개인정보 처리 범위를 먼저 합의한다. 기본 테스트 자산은 수치 랜드마크를 사용한다.
- 범위 밖 기능을 안정화 단계에 끼워 넣지 않고 `Tasks/`의 후속 작업으로 분리한다.

## 다음 단계와의 연결

이 문서는 초기 버전의 마지막 설계 단계다. 모든 완료 기준을 만족하면 테스트 근거와 실행 절차를 정리하고 해당 구현 작업을 `Tasks/`에서 완료 처리한다. 미달 항목은 재현 절차, 우선순위, 담당 영역을 포함한 후속 작업으로 등록한 뒤 관련 02~05 설계 단계로 되돌려 수정·재검증한다. 이후 대전 로직, 다중 손 또는 원격 연결 같은 확장은 별도의 기획과 설계 승인을 거쳐 진행한다.
